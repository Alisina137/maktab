# Admin Communication & Fees — Improvement Roadmap

Scope: the existing administrator route `/admin/communication`. The real repository is the source of truth for current behavior, and MaktabLink's MVP specification controls authorization and workflows. Preserve the existing audited, school-tenant-scoped communication/payment APIs unless a later phase explicitly adds backward-compatible contracts.

## Phase 1 — Navigation, dashboard correctness and responsive workspaces (implemented)

- Keep **Communication & fees** as one school-admin main navigation entry; add **Overview / Communication / Fees** accessible, visibly selected subtabs, first tab selected by default and auto-scrolled into view. Existing deep links to `/admin/communication` still land on Overview.
- Overview separates communication counts (total/published/scheduled/archived **announcements**, not claimed push deliveries) from financial metrics (issued invoice count, issued billed, net paid, outstanding, overdue outstanding, unique students owing, collection percentage). **Draft and cancelled invoices do not inflate collectible totals.** Empty billings display an em dash rather than a misleading zero-percent collection rate.
- Overview includes independently labeled recent announcements/invoices and navigation actions. The lists do not claim to be paginated, searched, or filtered server-side yet; Phase 2 and 3 will add that.
- Communication presents the existing create/scheduled-edit form alongside the authorized announcement list. Fees presents the existing draft-invoice/reminder form alongside invoice details, payment history and reversal actions. Desktop shows two panels side by side, each no wider than 600px. At <=1050px, the **List / Create** toggle shows one panel at a time, with List selected first. Existing form/API actions are preserved.
- `/v1/admin/communication`, `/v1/admin/families`, and `/v1/admin/academics` now load/retry independently. Losing the family or academic endpoint cannot blank the already loaded announcement/invoice list; the dependent creation form has a targeted loading/error/retry state. Each asynchronous response is bound to its initiating bearer token and its resource request generation, preventing stale account data from rendering after a school/account switch. The Communication/Fees resource remains the financial source of truth.
- Existing fetch calls share the admin API's typed network/error parsing. Forms retain a stable HTML form reference across await before resetting their values.
- UI tabs, summaries, button labels, and revenue explanations use English/Dari/Pashto admin translations, numeric grouping and responsive RTL handling.
- No new financial mutation, notification-delivery promise, online payment, database migration, or change to parent/student fee visibility. Existing payment retry/idempotency and immutable reversal mechanics are preserved.
- Tests: `pnpm verify:admin-communication:phase1` runs source/privacy/RTL guards plus `scripts/test-admin-communication-phase1-model.test.ts`; included in monorepo verification and Linux/Windows CI.

**Manual browser acceptance pending**: exact current school balances against issued invoices after payments and reversals; no zero-looking dashboard when communication endpoint fails; academic/family endpoint outage retaining read-only authorized lists; two concurrent admin sessions in different schools; narrow-width 320/375px, tablet, desktop, Dari/Pashto RTL, 200% browser zoom and screen reader; payment idempotency and cancellation flows. No manual browser run is claimed. Production remains **NO-GO** pending Step 20 external checks.

## Phase 2 — Announcements (implemented)

- The Communication list has title/body **search**, status filters (All/Published/Scheduled/Archived), audience filters (school/class/role), actual authorized class-name filters, and **20-at-a-time display pagination**. Expanded details include complete title/body, class and role audience, school-local publication date, status and record reference; editing is offered only for unpublished scheduled announcements.
- Added a new **school-admin-only** `POST /v1/admin/announcements/recipients/preview` endpoint. It reuses the database's actual `announcementRecipients` rules: eligible active accounts, class membership, optional role intersection, tenant ownership, unique account IDs, withdrawn students and suspended/archived users. The response contains **only an aggregate recipientCount** and schoolTimezone, never names or IDs. An invalid class returns 404; invalid audience fields fail validation. The preview does not issue announcements or mark delivery.
- The editor shows a debounced **current eligible recipient count** for the intended school/class/role with account-generation protection, clear loading/errors and a warning that scheduled membership can change before publication. It does **not** claim device receipt or push delivery.
- Publishing now and scheduling are explicit choices. Scheduled date/time is interpreted using the **school's saved IANA timezone**, independently of the administrator computer/browser time zone. Invalid dates and impossible daylight-saving times are rejected, and past scheduled instants are blocked. Scheduled-announcement edit can retain the original publication date when left blank. List publication dates use the verified school zone; while unavailable they are explicitly labeled UTC.
- Existing audited announcement lifecycle (immediate publish, scheduled update, archive) is unchanged; published text remains immutable. Archiving requires confirmation and warns that previously dispatched push notifications cannot be recalled.
- Announcement search/filter/paging is **client-side display paging of the existing authenticated school overview**, not backend cursor pagination or a reduced network payload. True server-side pagination and persistent drafts remain separate future API work and must not be claimed here.
- Native HTML form controls, role/status labels, screen-reader count/status, accessible actions, visual badges, English/Dari/Pashto translations and RTL small-screen layout are included.
- Automated verification: `pnpm verify:admin-communication:phase2` runs pure filtering/page/timezone tests and guards. The API integration suite tests recipient count matching actual published class audience, PARENT/STUDENT role intersections, privilege enforcement, validation, no side effects, and cross-school class rejection behavior.

**Manual acceptance still pending:** compare preview with actual eligible school users before/after suspension, test scheduled publication across DST in a non-Kabul school, Android browser and desktop date-picker RTL, archive and failed preview, 45+ announcements, slow requests, and notification delivery monitoring. Step 20 production status remains **NO-GO**. No migration. 

**Not included in Phase 2:** persistent draft announcements, content editing after publication, guaranteed delivery/read analytics, and backend cursor pagination. These require separately scoped lifecycle and storage changes.

## Phase 3 — Fee invoices (implemented)

- Invoice directory under Fees supports server-side, school-admin-only search across student name, student code, description and numeric invoice number; status, academic year, class and student filters; and 20-record server-side pages (sorted by creation timestamp and identifier), with local loading, retry and empty states. Results never expose invoices from another school, and the API enforces filter parameter validation.
- Database migration `0022_fee_invoice_numbers.sql` safely **backfills existing school invoices** with deterministic per-school numbers, creates unique school/number protection and initializes an atomic per-school invoice counter. New invoices receive a permanent number inside the creation transaction; cancelled invoices never release their assigned numbers. The UI displays `INV-000001`-style references. There is no claim of global numbering, fiscal-year sequences, or legal tax invoice compliance.
- The invoice detail is expandable, includes student, status, reference, due date, amount, paid/outstanding, and existing ledger/payment-history actions. Draft invoices offer a dedicated editor for student, amount, due date and description, backed by `PATCH /v1/admin/fees/invoices/:invoiceId`; this uses a row-locked state check, active/tenant-owned student validation, a required `updatedAt` optimistic concurrency token, and an atomic before/after audit event.
- Issued/paid/cancelled invoices **cannot be silently edited**. Issue and cancel now require explicit user confirmation; the backend continues to validate lifecycle transitions and financial ledger invariants.
- Mobile/tablet List/Form switching, RTL, keyboard tab navigation and localized status labels are preserved. The parent/student read-only endpoints remain unchanged except including the assigned immutable invoice number.
- Real API/DB integration tests cover 21 invoices split across pages, school-specific numbering, unauthorized edits and listings, optimistic edit conflicts, published-only parent visibility, and audit writes. The exact checks are available in `pnpm verify:admin-communication:phase3`, full `pnpm verify`, and Linux/Windows CI.
- **Migration required:** execute `pnpm db:migrate` once on the authorized database and then deploy the updated API. Do not deploy the updated API against an unmigrated database. Back up production before migration.
- **Known limitation:** the existing `GET /v1/admin/communication` overview still reads all authorized school invoices to calculate KPIs and their ledger. The new invoice directory itself is database-paginated; further separation and report-specific aggregate queries belong to Phase 4/6 performance work. The dedicated detail is a disclosure inside the list, not a separate route or fully fledged drawer.

**Pending manual verification:** deployed PostgreSQL migration/backfill/rollback planning, 320px to desktop including Dari/Pashto RTL, stale-session/slow response tests, and manual accounting review. Production remains **NO-GO** until Step 20 external evidence and operator sign-off.


## Phase 4 — Payments and student balances (implemented)

- Fees now has three internal workspaces: **Invoices / Payment history / Student balances**. Existing invoice creation and payment/reversal actions stay intact. Payments and balances have separate school-scoped, authorized retrieval, independent loading/error/retry, and session-generation stale-response protection.
- In an expanded invoice, the payment method is a controlled selector (**Cash, Bank transfer, Mobile money, Other**) rather than free-text. Input is validated as whole positive AFN no greater than outstanding; a confirmation states student, invoice number, chosen method, amount and projected remainder. Backend retains the locked row, idempotency token and append-only ledger for payment safety; confirmation does not bypass backend checks.
- New `GET /v1/admin/fees/payments` returns 20-record database pages of immutable **PAYMENT / REVERSAL** entries with filters for student, kind, method, recorder username and **school-local** from/to date. The listing displays actor, school-authenticated invoice number, timestamp and reference; no separate transaction-edit endpoint was added.
- New `GET /v1/admin/fees/students/:studentId/balance` calculates the single student's issued-invoice billed, ledger-paid, outstanding and overdue balances, excludes DRAFT and CANCELLED, and returns linked issued invoices including past payment/reversal totals. No parent/student or cross-tenant permission is introduced.
- New `GET /v1/admin/fees/payments/:paymentId/receipt` fetches school name, invoice/student identity, immutable original **PAYMENT** record, record-actor username, transaction reference, reversal state and **current** remaining balance from the backend. The UI lets admins print or Save as PDF using their browser's print dialog; it does **not** generate a server-signed PDF. Reversed receipts are explicitly marked invalid and original payments remain preserved.
- No database migration beyond Phase 3's required `0022_fee_invoice_numbers.sql`. These Phase 4 read endpoints use the existing schema; there is still no online payment collection, bank reconciliation, refund disbursement or currency conversion.
- Added authenticated API/DB integration regression for payment filters, receipt security and reversal validity, school isolation, parents forbidden, student financial totals, draft exclusion, audit/append-only ledger persistence. New `pnpm verify:admin-communication:phase4` source/RTL/accessibility guard is included in monorepo verification and Linux/Windows CI.
- Known limitations: database-paginated payment history applies date filtering by the school timezone but the history's user-visible print/date rendering still requires real-device browser testing. Receipt's current balance is **not** the balance at payment time; it is intentionally labeled current. No receipt is offered for a REVERSAL. Existing full admin communication overview still retrieves all school invoice ledgers for KPIs; aggregate performance work is deferred.
- Production remains **NO-GO** until exact deployed migration/DB restore, printed receipts in all three languages, independent accounting comparison, timezone edge cases, cross-tenant manual checks, concurrency, and external Step 20 acceptance are evidenced.

## Phase 5 — Notification delivery and fee reminders (implemented)

- Admin → Communication now has an expandable **Notification delivery monitor** with independently loaded tenant-scoped queue health. It reports PENDING (in-app queue), SENT (at least one provider-accepted device), FAILED (push attempt failed), as well as independently stored recipient read/unread totals. CANCELLED notification counts are excluded from read/unread. The latest 20 school notifications expose queue and per-device attempt aggregates, without device tokens or raw provider errors. **Provider accepted is not physical device delivered/read.** Real Expo delivery receipts and confirmed device receipt tracking are not implemented.
- New `GET /v1/admin/notifications/delivery` and `POST /v1/admin/notifications/:notificationId/retry` require School Admin. Retry is audited and permitted only when the current record is FAILED; it requeues for the next platform scheduler pass, not a direct provider send. Already accepted device rows remain SENT so they are not explicitly retried. Retrying archived announcements, withdrawn or suspended recipients, invalid fee alerts or fully paid/cancelled invoices is refused. The queue worker revalidates recipient membership at send time. Simultaneous background workers and exact provider receipt reconciliation still require deployment-level serialization and separate integration.
- Scheduler materialization heartbeat and last error now persist **per school** in `communication_settings` and are visible to its admin. UI distinguishes never observed from last success/attempt and warns for an observed success older than 36 hours. Heartbeat means recipient notification **materialization**, not that Expo accepted or recipients read them. Deployment cron and real push credentials must still be configured and verified outside the app.
- Fee reminder editing uses **structured day chips** and a 1–90 whole-day input: one to six unique days, removal and addition with server-enforced validation. Invalid tokens can no longer be silently dropped as in the legacy comma field. School timezone remains authoritative when the platform scheduler compares civil due dates; idempotent dedup keys prevent same-day duplication.
- The worker declines to push **stale FEE_DUE after due date**, premature FEE_OVERDUE, paid/cancelled/draft invoices, inactive students, suspended/archived users and archived or retargeted announcements. Historical in-app alerts are not erased solely because time passed; current invoice balances remain server-authoritative.
- Migration `0023_notification_scheduler_health.sql` adds per-school scheduler timestamps and last error to the existing communication settings. Apply after `0022_fee_invoice_numbers.sql` before deploying the new API. Linux/Windows source guards, PGlite store/API tests, TypeScript and build belong to `pnpm verify:admin-communication:phase5` and monorepo/CI validation; live scheduler + device acceptance **NOT RUN**.
- Limitations: currently no Expo push **receipt polling**, global scheduler lock, push claim leases, per-device backoff/budget management or historical delivery archive beyond latest 20. Retried FAILED messages remain subject to upstream provider/network ambiguity. Phase 7 must explicitly validate scheduled job concurrency, manual retry race conditions, school timezone and recipient withdrawal before production.
- **Production remains NO-GO** until independent Step 20 operator evidence, migration rehearsal, manual browser/RTL and physical Android push delivery tests are complete.

## Phase 6 — Reports and financial operations (implemented)

- Added a fourth Fees subtab **Reports & reconciliation** alongside Invoices, Payment history and Student balances. It shows current issued-invoice billed, net paid, outstanding and overdue totals, school-civil-day aging buckets (not due / 1–30 / 31–60 / 61–90 / >90 days) and transaction collections grouped by original payment method. DRAFT and CANCELLED invoices never inflate financial reporting.
- The **from/to** range is applied to the *transaction collection statement* (gross payments, immutable reversals, net collections) using the school's timezone. Current issued-invoice balances/aging are explicitly **as of today**, not retroactively reconstructed at an arbitrary historical date. A negative reversal row is preserved, and reversed cash/bank payments show REVERSED rather than being considered eligible for new matching.
- Added admin-only **GET /v1/admin/fees/reports** and **GET /v1/admin/fees/reports/export** (authorized JSON-wrapped downloadable CSV). Exports contain explicitly named columns, UTF-8 BOM, RFC-style double-quote escaping and neutralization of spreadsheet-formula prefixes including leading whitespace. Report/export datasets fail with validation when school reads exceed 5000 invoices, payments or reconciliation records; numbers are never silently truncated. CSV export is audited per school.
- Added independent **fee_payment_reconciliations** data in migration **0024_fee_payment_reconciliation.sql**. School admins can mark only original, unreversed CASH / BANK_TRANSFER payments as reconciled, with optional external reference, and reopen the reconciliation. Mutations are serialized with the invoice lock and audited atomically. The append-only fee_payments table and original payment/reversal amounts are never edited. Matching is a recorded **manual accounting declaration**; bank verification and gateway capture are not claimed.
- Added an admin-only audited **POST /v1/admin/fees/invoices/bulk-preview** endpoint. It validates 1–100 candidate invoices, flags missing/inactive/foreign-school students without disclosing identities, detects duplicate student/due-date/normalized-description keys both **within the batch** and among existing noncancelled invoices, and returns aggregate ready/duplicate/unavailable counts. It **does not create or issue any invoices**; staff must use the existing individual draft workflow. The UI provides active student selection, date, amount, description and a results view.
- No change to parent/student fee permissions or immutable payment storage. The monitor and exports guard token-identity switches. Dari/Pashto/English, Solar Hijri inputs, RTL accessible controls and responsive layout are included.
- CI verification: **pnpm verify:admin-communication:phase6** (source guards + CSV injection/reversal tests), database PGlite integration covering scope, ledger, reconciliation and duplicate-preview invariants, plus repository TypeScript/test/build on Linux and Windows.
- Deploy **0024** only after **0022** and **0023**, with production backup and migration rehearsal. Limitations include no online payment, no bank ingestion/matching automation, no historical point-in-time aging replay, a 5000-row report/export ceiling, and no bulk invoice creation. Real browser, RTL, external accounting comparison and production Step 20 acceptance are **NOT RUN / NO-GO**.

## Phase 7 — Integrated release verification (implemented code; manual acceptance pending)

- Updated fee reminder scheduler to lock each invoice before calculating current ledger and student eligibility. This prevents an overdue background job from overwriting a concurrently settled PAID balance and preserves the existing idempotent reminder de-duplication.
- Notification provider sends now use a conditional **30-minute expiring claim**, preventing overlapping cron workers and admin retries from handing off the same notification while the lease is active; claims are released on completion. Expo transport requests are bounded to 15 seconds. Multi-device partial failure remains FAILED/retryable rather than being incorrectly marked SENT when only one device was accepted; previously accepted device deliveries are not resent deliberately.
- Added `0025_notification_push_lease.sql`, after migration 0024; deploy only after a staging PostgreSQL rehearsal and database backup. The PGlite fixture migration lists include the new schema and the journal regression continues to apply the full chain.
- Added regression coverage for overlapping workers and mixed-device acceptance plus a Phase 7 source-level verification gate in Linux/Windows CI. A separate manual acceptance matrix explicitly covers real PostgreSQL contention, 2-school/role access, school-local timezone, scheduler termination/recovery, actual device push, RTL accessibility and exact build independent accounting signoff.
- **Known limitation:** transport ambiguity (provider acceptance without recorded acknowledgment) cannot be proved exactly-once by leases; a crashed worker's lease eventually expires and dispatch may be retried. Real Expo receipts, actual scheduler credentials and device receipt must still be checked outside CI.
- **PRODUCTION NO-GO:** manual tests and independent Step 20 production release signoff are NOT_RUN. See `docs/ADMIN-COMMUNICATION-FEES-PHASE7-ACCEPTANCE.md` and `docs/PHASE7-RELEASE-ACCEPTANCE.md`.

**Principles:** monetary reporting excludes drafts and cancellations; issuance and payment are explicit high-risk actions; never claim provider-accepted push as delivered/read; never infer parent payment collection from an app view; never weaken server tenant and recipient scopes.
